# Правила работы с репозиторием

## Контекст проекта

Celestial Cookie Consent — плагин для WordPress для управления согласием на использование cookies. Назначение и текущий статус описаны в `README.md`.

Репозиторий находится на начальном этапе. Не считайте запланированные функции реализованными. Не создавайте каркас, инфраструктуру сборки или зависимости без необходимости для текущей задачи.

## Архитектура плагина

- Следуйте документации WordPress по разработке плагинов и Gutenberg-блоков. Для регистрации блока и его ресурсов используйте `block.json` и стандартные API WordPress.
- `celestial-cookie-consent.php` — точка входа WordPress. Регистрирует страницу настроек, опции, обработчик формы, перевод и блок. Для блока нужен WordPress 6.5 или новее.
- Публичный баннер — динамический Gutenberg-блок `celestial-cookie-consent/banner` на Interactivity API. `src/block/banner/index.js` отвечает за редактор, `render.php` за серверную разметку, `view.js` за поведение на сайте. WordPress передаёт актуальные опции и переводы через `wp_interactivity_state()`. Базовые стили находятся в `src/block/banner/style.css`. Тема может переопределять их в `theme.json`, как описано в README.
- Плагин автоматически выводит баннер через `do_blocks( '<!-- wp:celestial-cookie-consent/banner /-->' )` и `wp_footer`. Если блок уже отрисован шаблоном или страницей, повторный вывод пропускается.
- Административный интерфейс — отдельная React-страница на компонентах WordPress в `src/backend/`. `index.js` связывает данные с формами, `hooks/` содержит состояние и операции с данными, `components/` отображает переданные данные. Административный пакет загружается только на странице настроек плагина.
- Текст баннера хранится в опции `celestial_cookie_consent_message`. Хук `useSettings` читает и сохраняет её через стандартный `/wp/v2/settings`. Список скриптов хранится в `celestial_cookie_consent_scripts`; React отправляет его через `admin-post.php`, обработчик проверяет POST, nonce и права `manage_options` и `unfiltered_html`.
- Используйте `npm run build` для выпуска и `npm run start:block` или `npm run start:backend` для разработки с пересборкой. Обе части используют стандартный `wp-scripts`; флаг `--experimental-modules` нужен блоку. Блок собирается в `build/block/banner/`, админка — в `build/backend/`. PHP выполняется WordPress.

## Общие правила

- Общайтесь с пользователем и ведите документацию на русском языке, если не запрошено иное.
- Используйте английский язык для идентификаторов в коде.
- Вносите изменения в пределах поставленной задачи. Сохраняйте чужие изменения.
- Обновляйте документацию, когда меняются поведение, установка или требования плагина.
- Не делайте коммиты, push и публикацию релизов без запроса пользователя.
- Для каждого релиза обновляйте [CHANGELOG.md](CHANGELOG.md). Добавляйте версию, дату и изменения, заметные пользователям. Синхронизируйте версию в заголовке плагина, `package.json` и `package-lock.json`.
- Не добавляйте секреты, персональные данные, дампы баз данных и локальные конфигурации в репозиторий.

## WordPress и PHP

- Используйте стандартные API WordPress и WordPress Coding Standards.
- Применяйте префикс `celestial_cookie_consent_` для глобальных функций, опций и хуков; для классов используйте согласованное пространство имён проекта.
- Используйте `celestial-cookie-consent` как slug и text domain.
- Подключайте ресурсы через API enqueue WordPress и только там, где они нужны.
- Защищайте PHP-файлы, не предназначенные для прямого вызова, проверкой `ABSPATH`.
- Проверяйте права доступа для административных действий. Используйте nonce для защиты изменяющих запросов; nonce не заменяет проверку прав.
- Проверяйте и очищайте входные данные, экранируйте вывод в соответствии с контекстом.
- Для SQL используйте API WordPress и подготовленные запросы там, где требуется собственный SQL.
- Подготавливайте пользовательские строки к переводу через функции локализации WordPress.
- Согласуйте минимальные версии PHP и WordPress и укажите их в документации и заголовке плагина до первого релиза.

## Согласие и интерфейс

- Необязательные скрипты, которыми управляет плагин, не должны запускаться до получения соответствующего согласия.
- Выбор хранится 180 дней в cookie `celestial_cookie_consent_choice` вместе с версией списка скриптов. Изменение списка требует нового согласия. Если запись cookie не подтверждается, покажите ошибку и не запускайте новые скрипты. При отзыве уже запущенного скрипта перезагрузите страницу после сохранения нового выбора.
- Код, введённый в админке, передаётся браузеру и может делать собственные сетевые запросы после согласия. Используйте только проверенный код без секретов. Плагин управляет запуском добавленных в него записей.
- Отказ и изменение согласия должны быть доступны пользователю. Ссылка `#cookie-preferences` повторно открывает настройки на странице с блоком, даже после сохранения выбора.
- Не заявляйте автоматическое управление cookies сторонних плагинов без реализованной и проверенной интеграции.
- Обеспечивайте работу с клавиатуры, видимый фокус, понятные подписи и корректное управление фокусом в диалогах.
- Не добавляйте телеметрию и внешние сетевые запросы без согласованной необходимости.
- Не обещайте юридическое соответствие только за счёт установки плагина.

## Проверка изменений

1. **Сборка.** После изменений JS или метаданных запустите `npm run build`. Проверьте, что созданы `build/block/banner/block.json`, `index.js`, `view.js` и файлы зависимостей блока, а также `build/backend/index.js` и `index.asset.php`. После изменений конфигурации сборки проверьте пересборку через `npm run start:block` и `npm run start:backend`.
2. **WordPress.** Используйте локальное окружение `wp-env`, описанное в [README.md](README.md). Откройте редактор Gutenberg, страницу **Настройки → Согласие на cookies** и публичную страницу с баннером. Проверьте, что блок доступен в редакторе, а на публичной странице есть ровно один экземпляр и в консоли нет ошибок плагина.
3. **Админка.** При изменении форм проверьте сохранение текста и добавление, редактирование и удаление тестовой записи со скриптом. Перезагрузите страницу и проверьте результат. При изменении обработчика проверьте, что GET, запрос с неверным nonce и запрос без прав не меняют опции.
4. **Баннер.** При изменении согласия начните с чистого профиля браузера или откройте `?debug` и нажмите **Reset consent**. Проверьте принятие всех, отказ от всех и выбор одного из двух безопасных тестовых скриптов. Перезагрузите страницу, отзовите ранее данное согласие и убедитесь, что отключённый скрипт больше не запускается. Проверьте ошибку при невозможности сохранить cookie и отсутствие внешних запросов от самого плагина.
5. **Доступность и языки.** При изменении интерфейса проверьте клавиатуру, закрытие диалога по Escape, возврат фокуса и русский и английский интерфейсы. Язык сайта применяется к баннеру, язык профиля — к админке.

Для PHP запускайте `php -l` на изменённых файлах. Для правок только в документации достаточно сверить команды, пути, ссылки и поведение с кодом. В отчёте укажите, что проверили и что осталось непроверенным. После проверок восстановите исходные настройки и удалите созданные тестовые записи.
